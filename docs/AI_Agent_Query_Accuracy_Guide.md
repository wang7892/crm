# 智能体查询准确性验证与知识维护

## 本次改进

- 理单员与联系专员统一为订单归属角色。外部合同/时间轴使用 `TRIM(ci.manager)`；CRM 订单使用同步后的 `owner_name`，跟单员仍使用 `merchandiser`。
- 时间轴开放关联的理单员、客户、产品、流程状态；CRM 订单开放实际发货日期。
- 原始人员、客户、订单号、产品条件在模型修复期间保留，最终执行前再次校验。明确人员默认精确匹配。
- 组织人员名单用于补充识别问题中明确出现的人员姓名，不硬编码具体员工。
- 旧订单意图先转为结构化计划，与通用查询走同一校验流程。模型失败不再回退为丢失条件的订单列表。
- 命中已审核业务规则后，修复仍失败则不执行错误计划。同数据源、相同配置字段表达式可以跨已配置关联校验，例如合同的 manager 规则用于时间轴查询。
- 订单笔数使用 `count_distinct(order_no)`；明细计数仍可用 `count(id)`。订单列表明确展示明细记录，未擅自合并不同业务明细。
- 金额求和/平均按币种分组，数量求和/平均按单位分组；文本字段不能求和。
- 时间窗口使用左闭右开区间，不包含下个月第一天。日期格式错误时拒绝查询，不转换成零或空值；明确的时分秒保留。
- 回答显示实际筛选口径。返回条数不再冒充总数；日期为空显示未记录的含义。

## 客户采购统计回归修复（2026-09-08）

经业务确认：客户采购按 `contract_info.release_date`（合同下单日期）筛选，品种为 `product_name`，数量为 `total_quantity`，按产品与单位分别求和。合同下单日期为空时不自动借用创建时间或时间轴日期；用户明确要求创建时间、交期时仍使用相应字段。

此前语义白名单遗漏合同下单日期，条件校验却要求合同查询使用未配置的 `order_time`；部分包含“订单”的合同查询还会被改写为加工明细查询，导致有效采购汇总被拒绝。现已补齐字段及日期别名，并保留外部合同计划的数据来源，再执行原有条件与权限校验。此类统计直接在合同表聚合，不通过时间轴关联累计数量。

回归题包括原问题“摩洛哥VANOS(FTH)最近3个月采购的品种是什么，数量是多少”、补充“按照下单日期”的问法和“近3个月采购订单按品种统计数量”。客户名是查询参数；同类问题不需要新增问法分支。自动测试验证实际生成的 SQL、绑定时间、分组、最终执行校验和人员/客户条件保留。

## 试用前

重新编译并重启后端进程，前端不需要修改。此次没有新增数据库迁移。

CRM 订单发货查询依赖既有 `V1.6.0_49` 字段迁移及 MLS 同步；确认实际环境已经有 `sales_order.warehouse_actual_ship_date`，并核对最近同步结果。代码和单元测试不能证明线上同步完整。

默认口径：本月未发货 = 本月下单且未记录实际发货日期。明确说“本月应交”按交期；“本月已发货”按实际发货日期。发货日期为空不能证明实际未发货，现阶段不根据日期推断部分发货/全部发完。

## 建议试用题库

在相同用户、数据状态下切换模型验证。表中姓名和客户名均为参数，替换为实际人员/客户即可。结果应与人工按同口径查询的结果比较，不要求 SQL 字符串或回答措辞相同。

| 类别 | 问题 | 核对重点 |
|---|---|---|
| 人员 | 张海芳本月未发货的订单有哪些？ | 人员、下单日期、发货日期三个条件同时存在 |
| 同义表达 | 本月未发货的订单有哪些，只查询张海芳未发货的订单 | 与上一题相同筛选口径 |
| 同义角色 | 理单员张海芳本月未发货的订单 | 理单员对应 manager/owner_name |
| 同义角色 | 联系专员张海芳本月未发货的订单 | 与理单员口径一致 |
| 换人 | 赵琳本月未发货的订单 | 不混入其他人的订单 |
| 另一角色 | 跟单员张海芳负责的加工明细有哪些？ | 使用 merchandiser |
| 时间 | 张海芳上个月未发货的订单 | 时间为上月，不沿用前端默认近30天 |
| 时间 | 张海芳2026年8月未发货的订单 | 截止到9月1日之前 |
| 交期 | 张海芳本月应交但未发货的订单 | 使用交期，不能用下单日期 |
| 已发货 | 张海芳本月已经发货的订单 | 发货日期在本月，且有记录 |
| 计数 | 张海芳本月有多少笔订单？ | 按 order_no 去重计数 |
| 分组 | 每个理单员本月订单数量是多少？ | 按理单员分组、按订单号计数 |
| 明细 | 本月加工明细有多少条？ | 明细数量，不冒充订单笔数 |
| 金额 | 每个理单员订单金额合计是多少？ | 按理单员和币种分组；另需核实金额所属粒度 |
| 数量 | 产品数量合计是多少？ | 按单位分组，不直接混加米与码等单位 |
| 采购 | 摩洛哥VANOS(FTH)最近3个月采购的品种是什么，数量是多少 | 合同下单日期筛选，产品与单位分组，合同数量求和 |
| 采购同义问法 | 某客户近3个月采购订单按品种统计数量 | 保留合同来源，不因“订单”二字改查加工单 |
| 订单号 | 查询某个准确订单号的状态 | 使用明确订单号，不混入后缀不同的订单 |
| 客户 | 某客户本月下单的订单有哪些？ | 客户及下单日期都被过滤 |
| 客户名称 | 名字中带有印尼的客户有哪些？ | 名称包含条件，不把“印尼”当作人员 |
| 来源 | 客户来源是展会客户的客户有哪些？ | 使用客户来源字段 |
| 未跟进 | 某联系专员名下未记录跟进时间的客户 | 人员和跟进日期空值条件同时存在 |
| 空结果 | 一个确实不存在的订单号 | 显示无符合条件记录，不自动放宽条件 |
| 数据不足 | 哪些订单全部发完？ | 单个发货日期不足时说明缺少数量依据 |

每题记录：问题、用户、模型、时间、查询口径、正确订单号集合/统计值、实际结果、追踪ID、是否正确、是否能够回答。正确率和可回答覆盖率分别统计。

## 定位错误

查询工具记录中包含 `trace`。后端 DEBUG 日志按同一 ID 串联：

- `stage=parsed`：原问题、模型、命中规则ID和模型计划。
- `stage=validation-rejected`：约束或字段校验不通过。
- `stage=execute`：最终实体、类型、字段、分组、SQL和绑定参数（敏感字段参数脱敏）。
- `stage=result`：返回行数、警告和耗时。

日志用于管理端排查，SQL和原始参数不显示在业务回答中。生产环境按现有日志权限及保留策略管理。

## 公司知识库维护

普通文档用于补充解释；影响字段选择、过滤或计算的业务定义应使用现有业务规则提取、审核、发布流程。发布后用知识检索测试确认匹配字段与筛选规则。

每条定义建议包含：术语、同义词、适用领域、明确含义、映射字段、必要条件、不可替代的字段、空值/异常说明、正反例、生效时间。

例：订单理单员就是 CRM 联系专员，源字段为 contract_info.manager；不能使用跟单员 merchandiser 替代。不要把真实员工姓名写成固定术语过滤条件，应由每次问题提供人员值。

基础字段、允许的关联和执行能力仍由后端白名单约束。知识库不会自动创建新表关联或扩大查询权限。

## 验证边界

自动测试覆盖查询计划和SQL构造、修复与执行拦截、展示口径，不调用真实模型或业务数据库。因此不代表线上问答准确率。

本次未新增任意 JOIN、OR 条件树、通用 NOT EXISTS 查询引擎，也未建立整库数据质量审计。无法表达的复杂问题应明确说明条件/能力缺失；不能把正向列表当作排除查询的答案。

订单号是否跨组织/历史版本唯一、合同与时间轴是否一对一、人员同步映射是否正确、发货字段是否完整，仍需使用实际数据核实。当前订单计数沿用所选数据源及权限范围内的 order_no 口径。
